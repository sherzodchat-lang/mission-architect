# Mission Architect — полное описание игры

Документ для ИИ-агента, который будет писать игру. Здесь всё, что нужно для реализации: правила, формулы, данные, экраны, дизайн, звук и порядок работы. Тексты интерфейса — на английском (как в макетах), пояснения — на русском.

- **Что это:** браузерная игра для NASA Space Apps Challenge 2026, челлендж «Space Mission Design Game».
- **Суть:** игрок проектирует космическую миссию (аппарат, орбита, ракета, наземные станции), запускает симуляцию на 12 месяцев и получает разбор, почему миссия удалась или нет.
- **Главная ценность:** каждое решение имеет цену в других ресурсах, единственно верного решения нет, а причины успеха и провала объясняются простым языком.
- **Срок:** один день разработки. Поэтому есть приоритеты P0 / P1 / P2 (раздел 13); P1 не начинать, пока P0 не принят.

### 1.1. Намеренные отступления от макетов

1. **Изображения в карточках остаются пустыми** (раздел 10.3). Ни одной сгенерированной или стоковой картинки в карточках.
2. **Нет логотипа NASA** нигде: ни на аппарате, ни в отчёте, ни в шапке. Названия реальных миссий пишутся текстом.
3. **Схема аппарата в центре экрана 03 — плоская SVG-схема** со слотами, а не 3D-рендер. Кнопки `Rotate` нет.
4. **Числа на макетах игнорировать** (цены ракет, время связи 7.2 часа, 48/50 GB и т. д.) — они несогласованы между экранами.
5. **Наземные станции** для земной миссии — Wallops, Santiago, Fairbanks, Svalbard, а не Goldstone/Madrid/Canberra (те — сеть дальней связи, они появятся в лунной и марсианской миссиях).
6. **Орбита GEO** показана, но недоступна для кубсата, с объяснением почему.
7. **Лунная и марсианская миссии** открываются по звёздам (раздел 8.2); для показа жюри есть переключатель «открыть всё» (раздел 13).
8. **Полка на главном меню** — это коллекция открытых реальных миссий-аналогов, а не список типов миссий.
9. **Четвёртая оценка в отчёте** в одиночной игре называется `Operations`, в командной — `Teamwork`.

## 2. Стек и структура проекта

- **Vite + React + TypeScript + Tailwind CSS**, без сервера.
- **Zustand** — состояние игры. **Howler.js** — звук. **Vitest** — тесты движка.
- **Графика:** SVG в компонентах. Three.js не использовать в P0.
- **Сохранения:** `localStorage`.
- **Деплой:** статическая сборка (GitHub Pages или Vercel), репозиторий публичный.

```
src/
  data/        # missions.ts, components.ts, orbits.ts, launchers.ts, stations.ts,
               # events.ts, glossary.ts, analogs.ts, voiceLines.ts
  engine/      # budget.ts (расчёт ресурсов), simulate.ts, scoring.ts, rng.ts — чистые функции
  store/       # gameStore.ts, settingsStore.ts
  screens/     # MainMenu, MissionSelect, Builder, OrbitLaunch, Simulation, Report, HowToPlay
  components/  # Panel, Button, Stepper, Gauge, ResourceStrip, ImageSlot, Tooltip, Modal, ...
  audio/       # audioManager.ts, audioManifest.ts
public/
  audio/voice/ audio/sfx/ audio/ambient/
  images/cards/   # пусто; сюда позже можно положить картинки
tools/balance_check.py   # эталонная проверка баланса (уже лежит в проекте)
```

**Правило архитектуры:** движок (`engine/`) не импортирует React и не знает про интерфейс. Интерфейс только вызывает функции движка и показывает результат.

## 3. Игровой цикл

1. **Main menu** → `New Mission`, `Team Mode (2–4 players)`, `How to Play`, `Continue last design`.
2. **Mission** — выбор сценария.
3. **Design** — сборка аппарата из компонентов, живой пересчёт шести ресурсов.
4. **Orbit / Launch** — орбита, ракета, наземные станции, уровень испытаний.
5. **Operations** — симуляция 12 месяцев с событиями и решениями.
6. **Report** — счёт, разбор причин, реальная миссия-аналог, кнопка `Redesign and relaunch`.

Степпер в шапке: `Mission → Design → Orbit → Launch → Operations` (как в макетах). Экран 04 закрывает шаги `Orbit` и `Launch`: шаг `Orbit` получает галочку после выбора орбиты, шаг `Launch` — после выбора ракеты. Отчёт вне степпера.

Назад можно вернуться на любой предыдущий шаг до старта симуляции; выбор сохраняется. Кнопки `Undo` / `Redo` / `Reset` на экране сборки работают по истории состояний дизайна.

## 4. Ресурсы

Шесть ресурсов показываются всегда: на экране 03 — столбиками (панель `Resource budget`), на экране 04 — полосой внизу. Все шкалы в одном формате **«использовано / доступно»**.

| Ресурс | Использовано | Доступно |
|---|---|---|
| **Mass**, kg | корпус + все компоненты | лимит миссии и грузоподъёмность ракеты (меньшее) |
| **Power**, W | потребление всех систем | выработка панелей × доля солнца на орбите |
| **Budget**, $M | корпус + компоненты + запуск + станции + испытания + штраф за просрочку | лимит миссии |
| **Data**, GB | буфер, нужный на случай сбоя связи (половина месячной генерации) | память бортового компьютера |
| **Comms**, GB/mo | данные, которые приборы создают за месяц | пропускная способность канала за месяц |
| **Time**, months | срок разработки | лимит миссии |

Цвет шкалы: зелёный — запас ≥ 5%; жёлтый — запас меньше 5% или превышение, с которым лететь можно; красный — критическое превышение.

В лунной и марсианской миссиях добавляется седьмая шкала **Fuel (Δv)**, m/s: «нужно для перелёта, выхода на орбиту и её поддержания / даёт двигательная установка при текущей массе». Она показывает главный урок этих миссий: чем тяжелее аппарат, тем меньше манёвров даёт то же топливо.

### 4.1. Критические ошибки и предупреждения

**Критические (красные, запуск заблокирован):**
- масса больше лимита миссии или грузоподъёмности выбранной ракеты;
- бюджет превышен;
- выработки не хватает даже на служебные системы (компьютер, радио, ориентация, корпус);
- не выбран обязательный компонент: хотя бы один прибор, панели, батарея, радио, компьютер, система ориентации;
- ракета не летает на выбранную орбиту; не выбрана ни одна наземная станция;
- (Луна, Марс) топлива не хватает, чтобы добраться до орбиты и удержаться на ней;
- (Марс) срок разработки превышен — стартовое окно к Марсу открывается раз в 26 месяцев, опоздать нельзя.

**Предупреждения (жёлтые, лететь можно после подтверждения «Launch at your own risk»):**
- энергии хватает на служебные системы, но не на все приборы — приборы будут работать неполное время;
- батарея мала — приборы отключаются в тени, батарея изнашивается;
- канал связи уже генерации — часть данных не дойдёт до Земли;
- памяти не хватает на буфер;
- срок разработки превышен — каждый лишний месяц стоит $0.15M и −2 очка;
- прибору не хватает точности наведения.

Каждое сообщение состоит из трёх частей, как на макете 03: **что** («Power deficit»), **почему** («Instruments need 14 W, panels supply 9 W») и **что сделать** («Add solar capacity or remove an instrument»). Это обязательное правило для всех предупреждений в игре.

## 6. Формулы

Формулы общие для трёх миссий; различаются только данные и параметры миссии (`platform`, `baseTime`, `overFee`, `solarFactor`, `stepMonths`, опорная масса для Δv). Обозначения: `p` — уровень наведения (0 none, 1 coarse, 2 fine); `k` — батарейный коэффициент орбиты (для обеих земных орбит `k = 2`).

```
mass   = масса платформы + Σ kg всех компонентов и опций
time   = baseTime + Σ мес. компонентов + ожидание ракеты + мес. испытаний (+ перенос запуска)
over   = max(0, time − лимит срока)                # для Марса over > 0 — критическая ошибка
budget = цена платформы + Σ $M компонентов и опций + ракета + Σ станций + испытания + overFee × over

supply      = выработка панелей × доля солнца орбиты × solarFactor × состояние панелей
busLoad     = W платформы + W радио + W компьютера + W ориентации
instLoad    = Σ W приборов
demand      = busLoad + instLoad
duty        = clamp((supply − busLoad) / instLoad, 0, 1)      # доля времени работы приборов
если ёмкость батареи < k × demand:  duty × доля солнца, батарея помечается как undersized

coverage    = min(1.1, покрытие орбиты × множитель ракеты)
generated   = Σ GB/mo приборов × duty × coverage               # GB в месяц
capacity    = GB/mo радио × Σ единиц контакта выбранных станций × множитель радио при p
bufferNeed  = 0.5 × generated                                   # сравнивается с памятью
quality     = Σ(GB/mo_i × ценность_i × качество_i(p)) / Σ GB/mo_i

# только Луна и Марс
cruise      = шагов в пути у ракеты + добавка двигателя (SEP: +1)
dvHave      = Δv установки × опорная масса / mass
dvNeed      = Δv перелёта ракеты + Δv выхода на орбиту + Δv поддержания × (12 − cruise)
если dvHave < dvNeed — критическая ошибка

scienceSteps = последний шаг работы − cruise − задержка орбиты − 0.5     # 0.5 — ввод в строй
за шаг аппарат создаёт и передаёт  generated × stepMonths  и  capacity × stepMonths
```

Для земной миссии `cruise = 1`, двигателя нет, `stepMonths = 1` — получается раздел 7.1 как частный случай.

Шкала `Comms` показывает `generated / capacity`, шкала `Data` — `bufferNeed / память`, шкала `Fuel (Δv)` — `dvNeed / dvHave`.

## 7. Симуляция (экран 05)

Симуляция идёт по месяцам. Один месяц длится 6 секунд на скорости `1x` и 1.5 секунды на `4x`; есть `Pause`. При событии с решением симуляция останавливается («The simulation is paused until you decide»).

Генератор случайных чисел — с зерном (`mulberry32`). Зерно сохраняется в отчёте, в тестах фиксировано; `Redesign and relaunch` берёт новое зерно.

### 7.1. Фазы

| Месяц | Фаза | Наука |
|---|---|---|
| 1 | Launch & deployment | 0% |
| 2 | Commissioning | 50% |
| 3–12 | Science | 100% |

На орбите LEO миссия заканчивается после месяца 11 (вход в атмосферу, NASA GMAT); в месяце 9 в журнале появляется предупреждение.

Таблица выше — для земной миссии. Для Луны и Марса шкала времени та же (12 шагов), но шаг и фазы другие:

| Миссия | Длина шага | Путь | Выход на орбиту и ввод в строй (наука 50%) | Наука |
|---|---|---|---|---|
| Lunar Orbiter | 1 месяц | шаги 1…`cruise` (1 или 3) | следующий шаг | остальные |
| Mars Probe | 2 месяца | шаги 1…`cruise` (4 или 5) | следующий шаг; для `aerobrake` затем ещё 2 шага торможения без науки | остальные |

Подпись шкалы времени: `Mission timeline • 12 months` для Земли и Луны, `Mission timeline • 24 months` для Марса; в пути под аппаратом показывается расстояние до цели вместо луча к станции.

### 7.2. Шаг месяца

```
1. Определить событие месяца (не больше одного события с решением за месяц).
2. Посчитать duty и generated этого месяца с учётом фазы, событий и состояния приборов.
3. stored += generated
4. downlinked = min(stored, capacity этого месяца);  stored −= downlinked
5. если stored > память:  lost += stored − память;  stored = память
6. returned += downlinked;  science += downlinked × quality
7. Обновить здоровье аппарата, телеметрию, журнал, графики.
8. Если health ≤ 0 — миссия потеряна, симуляция останавливается.
```

Здоровье аппарата (`health`) начинается со 100.

## 8. Оценка и отчёт (экран 06)

### 8.1. Счёт (100 очков)

| Категория | Очки | Формула |
|---|---|---|
| **Science return** | 30 | `30 × min(1, science / цель)`; цель: Земля 100, Луна 720, Марс 2700 |
| **Resource efficiency** | 25 | сумма по четырём запасам: масса 5, энергия 7, бюджет 7, срок 6; каждый × `f(запас)` |
| **Reliability** | 25 | `25 × (0.6 × health/100 + 0.4 × отработанные месяцы / 12)` |
| **Operations** (соло) / **Teamwork** (команда) | 20 | соло: `20 × returned / generated`; команда — раздел 9 |

Запас = `(доступно − использовано) / доступно`; для энергии `(supply − demand) / supply`; для бюджета считается итоговый расход после полёта.

```
f(запас) = 0    если запас < 0
           0.7  если 0 ≤ запас < 5%       # слишком впритык
           1.0  если 5% ≤ запас ≤ 25%     # здоровый запас
           0.8  если 25% < запас ≤ 40%
           0.5  если запас > 40%          # ресурс простаивает
```

Штраф: −2 очка за каждый месяц просрочки разработки.

### 8.2. Исход и звёзды

Обязательный возврат данных: Земля 50 GB, Луна 500 GB, Марс 1200 GB.

- **Mission Success** — возвращено не меньше обязательного объёма и аппарат дожил до конца.
- **Partial Success** — возвращено от половины до полного обязательного объёма либо аппарат потерян после полного возврата.
- **Mission Failure** — остальное.
- **Звёзды:** ★ от 40 очков, ★★ от 65, ★★★ от 85. Три звезды даются только при Mission Success, две — не ниже Partial Success.
- **Открытие миссий:** две звезды на земной миссии открывают лунную, две на лунной — марсианскую.

### 8.3. Блок «What happened and why»

Три-четыре карточки, выбираются автоматически по правилам (первые сработавшие по убыванию влияния на счёт):

| Условие | Заголовок | Суть объяснения | Next time |
|---|---|---|---|
| `returned / generated < 0.8` | Antenna too small | «N% of science data never reached Earth» + цепочка `Sensor → Onboard storage → Antenna (bottleneck) → Earth` | upgrade the radio or add ground contacts |
| `duty < 0.9` | Power was tight | приборы работали N% времени | add solar capacity or schedule the payload |
| батарея undersized | Battery too small for eclipses | приборы отключались в тени | add battery capacity |
| качество < 0.8 из-за наведения | Blurry science | прибору нужна точная ориентация | upgrade attitude control |
| `lost > 0` | Storage overflow | N GB стёрто до передачи | bigger computer memory or more contacts |
| `over > 0` | Schedule overrun | N месяцев просрочки стоили $X | fewer new developments or less testing |
| запас по ресурсу > 40% | Unused capacity | ресурс простаивал | spend the margin on science |
| решение в событии сработало | Good decision: … | что именно удалось избежать | — |
| решение привело к повреждению | Risk did not pay off | что потеряно | protect the spacecraft first |
| LEO и миссия кончилась на месяце 11 | Orbit decayed | 1 месяц науки потерян | choose a higher orbit |

Карточка хорошего решения — зелёная, урок — жёлтая, потеря — красная.

## 9. Командный режим (P1, одно устройство, 2–4 игрока)

Игроки по очереди садятся за одно устройство. Между ходами — экран-заставка «Pass the console to: Systems Engineer».

| Роль | Чем управляет | Личная цель |
|---|---|---|
| **Science Lead** | вкладка `Instruments` | `Σ(GB/mo × ценность × качество) × duty × coverage ≥ 9` |
| **Systems Engineer** | `Power`, `Computer`, `Attitude control` | запас по энергии ≥ 10% и по массе ≥ 5% |
| **Comms & Ground Lead** | `Comms`, наземные станции | `capacity ≥ generated` и буфер помещается в память |
| **Mission Manager** | ракета, испытания, бюджет и срок | остаток бюджета ≥ $0.30M и срок ≤ 12 месяцев |

- При 3 игроках Mission Manager объединяется с Systems Engineer; при 2 — пары Science + Comms и Systems + Manager.
- Каждый игрок меняет только свои вкладки, но видит все ресурсы и цели остальных.
- После шага `Design` и после шага `Launch` — экран **Review board**: каждая роль видит статус своей цели и голосует `Approve` или `Request change` (с причиной из готового списка). Запуск возможен при всех `Approve`.
- У Mission Manager два жетона `Override`: продавить решение без согласия. Каждый жетон — −3 очка Teamwork.
- События в полёте решает владелец системы: вспышка и сбой ПО — Systems Engineer, отказ станции — Comms Lead, раскрытие панелей и маховик — Systems Engineer; на экране видны рекомендации остальных ролей.
- **Teamwork (20 очков):** `5 × число выполненных личных целей` (при 2–3 игроках — пропорционально), минус штрафы за `Override`.

## 12. Баланс и тесты

В проекте лежит `tools/balance_check.py` — эталонная реализация формул разделов 5–6 и 8 без случайных событий, с данными всех трёх миссий (`python3 tools/balance_check.py earth|lunar|mars`). Перебор всех вариантов после калибровки по данным NASA (SOA 2025, CubeSat 101, GMAT R2026a; подробности и старые значения — `src/data/nasa/calibration.md`) дал:

|---|---|---|---|---|
| Допустимых дизайнов | 199 813 | 676 658 | 360 256 | `balance_check.py` |
| Выполняют обязательный возврат данных | 17 630 (8.8%) | 1 736 (0.26%) | 1 154 (0.32%) | `balance_check.py` |

| Счёт: медиана / 99-й процентиль / максимум | 58 / 83 / 95.5 | 67 / 82 / 94.3 | 66.5 / 81 / 91.9 | `balance_check.py` |

- Сложность растёт как задумано: на Земле успешна примерно каждая одиннадцатая допустимая сборка, на Луне и Марсе — одна из 300–400; у Марса меньше всего сборок на 85+ и самый низкий максимум.

- Сборка «всё самое лучшее» нигде не проходит по массе и бюджету.
- На Луне главный ограничитель — масса (топливо съедает до половины аппарата), на Марсе — бюджет и срок.
- Прежний перекос «на Марсе побеждает электрическая тяга» снят калибровкой Δv по SOA: в лучшем 1% biprop 1 859, sep 1 352, biprop_xl 391. Орбиты Марса в лучшем 1%: aerobrake 1 612, capture 1 106, direct 884. На Луне по-прежнему чаще всего побеждают неподвижные панели (fixed 5 282 из 6 766) — при настройке первым делом смотреть сюда.

**Обязательные тесты движка (Vitest):**
1. Перенести проверки скрипта: движок на TypeScript даёт те же числа для 5 контрольных дизайнов из вывода скрипта.
2. Сборка из самых дорогих компонентов даёт минимум две критические ошибки.
3. Самая дешёвая сборка летит, но не возвращает 50 GB.
4. Симуляция с фиксированным зерном воспроизводима.
5. Сумма четырёх категорий равна итоговому счёту (с учётом штрафа).

Если агент меняет числа, он заново запускает перебор и сохраняет свойства из списка выше.

## 14. Звук (ElevenLabs)

Звук генерируется через подключённый MCP-сервер `elevenlabs` (тариф Starter, 40 000 кредитов). Язык озвучки — английский.

### 14.1. Правила расхода

1. Создать один поток: `creative_create_flow` с именем `Mission Architect audio`; все генерации — в него.
2. Перед каждой группой генераций вызвать инструмент с `estimate_only: true` и сложить стоимость.
3. **Потолок — 12 000 кредитов на всё.** Если оценка выше — остановиться и спросить пользователя.
4. Никогда не повторять вызов генерации «на всякий случай»: повтор списывает кредиты второй раз.
5. Число вариантов: речь — 2, эффекты — 2 (передать `generations_count: 2`).
6. Музыкальную модель не использовать; фон делается эффектом с `loop: true`.
7. После генерации опрашивать `creative_get_flow_run_status` до завершения, выбрать лучший вариант, сохранить файл в `public/audio/...`. Если прямой ссылки на файл нет — вывести пользователю список, что скачать из потока вручную, и продолжить работу без звука.
8. Перед массовой генерацией сделать одну пробную реплику (`v10_first_contact`) и сверить реальный расход с оценкой.

### 14.2. Голос

- Подобрать через `creative_list_voices`: спокойный уверенный руководитель полёта, американский английский, средний возраст (`descriptives`: calm, confident, professional). Один голос на все реплики. `voice_id` брать только из ответа инструмента.
- Модель: `eleven_v4`.
- Обработка «по радио»: узел `audio-effects` с `filter_preset_id` из доступных (`old_radio`, `phone`, `bright_phone`) — попробовать на пробной реплике и выбрать разборчивый вариант. Обработка бесплатная.

### 14.5. Звуковой движок

- `audioManifest.ts` — список всех файлов; `audioManager.ts` — три канала: `voice` (очередь, реплики не накладываются), `sfx`, `ambient` (громкость 0.25, приглушается до 0.1 на время реплики).
- **Отсутствующий файл не ломает игру:** событие просто проходит без звука, без ошибок в консоли.
- Звук включается только после первого клика пользователя (ограничение браузеров).
- Кнопка `Sound: On / Off` в шапке, состояние в `localStorage`.
- **Субтитры:** каждая реплика показывается всплывающей строкой `MISSION CONTROL: …` и записью в журнале — игра понятна и без звука.
- Файлы: mp3, моно, 96–128 kbps; при наличии `ffmpeg` выровнять громкость.

## 15. Сохранение

`localStorage`, ключи с префиксом `ma_`:
- `ma_settings` — звук, пройдено ли обучение;
- `ma_progress` — звёзды по миссиям, открытые аналоги;
- `ma_draft` — текущий незавершённый дизайн (автосохранение, статус `Autosaved` в шапке);
- `ma_saves` — до 5 сохранённых дизайнов с названием и счётом.

Все чтения и записи — в `try/catch`; игра работает и без хранилища.
